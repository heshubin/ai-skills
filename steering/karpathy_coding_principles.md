# Karpathy 编码原则

编写、修改、调试、重构代码时必须遵守的行为准则。

## 1. 先想清楚再动手
- 明确说出你的假设。不确定就问。
- 如果有多种理解方式，列出来让用户选，不要自己默默选一个。
- 如果有更简单的方案，主动提出来。

## 2. 简单优先
- 不做用户没要求的功能。
- 不为只用一次的代码搞抽象。
- 能用 50 行写完的不要写 200 行。

## 3. 精准修改
- 不要"顺手改进"旁边的代码、注释或格式。
- 匹配项目已有的代码风格。
- 每一行改动都必须能追溯到用户的需求。
- 清理你自己改动导致的无用 import/变量，不要删别人的。

## 4. 目标驱动
- 动手前先定义成功标准。
- "修 bug" → 先复现，再修，再验证。
- 多步任务先列计划，每步都有验证点。

## 5. 用最优方案，不用折中方案
- 改代码时直接用最优方案实现，不要用折中或临时方案。
- 如果有多种方案，选最干净、最彻底的那个。
- 折中方案会留下技术债，后续还要再改一遍。

## 6. 代码即文档，不要让读者猜
- 代码结构必须自解释，不能依赖注释来弥补设计缺陷。
- SQL 返回类型必须匹配实际查询的数据结构，不要用占位符（如 `0 AS rec_id`）凑别的表的 resultMap。
- 变量名、方法名、参数名要准确反映用途，不要复用语义不匹配的结构。
- 如果一段代码需要额外解释"为什么这样写"，说明设计有问题，应该重构而非加注释。

## 7. 禁止全限定类名，必须用 import
- 注解、字段声明、方法参数中使用类时，必须在文件顶部 import，然后用短类名。
- 禁止 `org.springframework.transaction.annotation.Propagation.REQUIRES_NEW` 这种内联全限定写法。
- 正确做法：`import org.springframework.transaction.annotation.Propagation;` + `@Transactional(propagation = Propagation.REQUIRES_NEW)`
- 唯一例外：两个同名类冲突时，频率低的那个可以用全限定。
