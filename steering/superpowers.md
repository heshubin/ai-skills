# Superpowers - 工程级开发流程

Superpowers 是一套完整的软件开发工作流程，确保代码质量和开发纪律。

## 核心原则

1. **设计优先** - 在编写代码之前必须先设计
2. **测试驱动** - 先写测试，再写代码
3. **系统化调试** - 使用结构化方法而非随机尝试
4. **任务分解** - 将大任务分解为 2-5 分钟的小任务

---

## 1. Brainstorming - 头脑风暴

### 触发条件
当用户要求创建功能、构建组件、添加功能或修改行为时，必须先进行头脑风暴。

### 硬性规则
⚠️ **在呈现设计并获得用户批准之前，不得编写任何代码或采取任何实现行动。**

这适用于每个项目，无论其看起来多么简单。

### 流程

#### 1. 探索项目上下文
- 检查现有文件、文档、最近的提交
- 评估项目范围
- 如果项目太大，帮助用户分解为子项目

#### 2. 询问澄清问题
- 一次问一个问题
- 尽可能使用多选题
- 理解目的、约束、成功标准

#### 3. 提出 2-3 种方法
- 包含权衡分析
- 给出你的推荐和理由
- 首先介绍推荐的选项

#### 4. 呈现设计
- 根据复杂度分段呈现
- 每段后询问是否正确
- 涵盖：架构、组件、数据流、错误处理、测试

#### 5. 编写设计文档
- 保存到 `docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`
- 提交到 git

#### 6. 规格自审
检查：
- 占位符（TBD、TODO）
- 内部一致性
- 范围是否合理
- 是否有歧义

#### 7. 用户审查
要求用户审查书面规格，等待批准后再继续。

#### 8. 过渡到实现
进入 Writing Plans 阶段。

## 2. Test-Driven Development - 测试驱动开发

### 触发条件
当用户提到 "TDD"、"测试驱动"、"先写测试" 时强制执行。

### TDD 循环

```
🔴 RED → 🟢 GREEN → 🔵 REFACTOR
```

#### 🔴 RED - 编写失败的测试
1. 编写描述期望行为的测试
2. 运行测试，确认失败
3. 提交失败的测试

#### 🟢 GREEN - 使测试通过
1. 编写最少的代码使测试通过
2. 不要过度设计
3. 运行测试，确认通过
4. 提交通过的代码

#### 🔵 REFACTOR - 重构
1. 查看代码，寻找改进机会
2. 重构代码
3. 运行测试，确认仍然通过
4. 提交重构后的代码

### 硬性规则
1. **先写测试** - 在编写实现代码之前必须先写测试
2. **删除未测试的代码** - 如果在测试之前写了代码，必须删除
3. **小步前进** - 每次只添加一个小功能
4. **频繁运行测试** - 每次修改后都要运行测试

### 测试反模式（禁止）
- ❌ 先写代码再写测试
- ❌ 测试实现细节而非行为
- ❌ 测试之间有依赖
- ❌ 不运行测试就提交

## 3. Systematic Debugging - 系统化调试

### 触发条件
当遇到 bug、错误、异常或用户说"不工作"时使用。

### 四阶段流程

#### 阶段 1：复现问题
- 记录详细的问题描述
- 记录复现步骤
- 记录预期 vs 实际行为
- 确认可以稳定复现
- 记录环境信息

#### 阶段 2：隔离根因
使用以下技术：
- **日志注入** - 在关键点添加日志
- **二分法** - 注释掉一半代码，看问题是否消失
- **Git bisect** - 找到引入 bug 的提交
- **最小复现** - 创建最小复现用例

#### 阶段 3：验证假设
1. 基于隔离结果提出假设
2. 设计验证实验
3. 执行实验并记录结果
4. 如果假设错误，回到阶段 2

#### 阶段 4：修复并验证
1. 实施修复
2. 运行所有相关测试
3. 手动验证修复
4. 添加回归测试
5. 提交修复

### 禁止的行为
- ❌ 随机尝试修复
- ❌ 假设而非验证
- ❌ 修复症状而非根因
- ❌ 不添加回归测试

## 4. Writing Plans - 编写实现计划

### 触发条件
在完成 Brainstorming 并获得设计批准后使用。

### 计划结构

每个任务应该：
- **2-5 分钟可完成**
- **有明确的验证标准**
- **尽可能独立**
- **包含具体的文件路径**

### 计划模板

```markdown
# 实现计划：<功能名称>

## 概述
简要描述要实现的功能和目标

## 任务列表

### 任务 1：<任务名称>（预计 X 分钟）
- 具体步骤 1
- 具体步骤 2

**验证：**
- 如何验证任务完成

**文件：**
- `path/to/file.py`

### 任务 2：...

## 验收标准
- [ ] 所有测试通过
- [ ] 功能符合设计文档
- [ ] 代码已审查

## 依赖关系
- 任务 2 依赖任务 1
- 任务 3 可以与任务 2 并行
```

### TDD 任务分解
如果使用 TDD，每个功能应该分为：
- 任务 N.1：编写测试（RED）
- 任务 N.2：实现功能（GREEN）
- 任务 N.3：重构（REFACTOR）

### 计划后
1. 保存到 `docs/superpowers/plans/YYYY-MM-DD-<主题>-plan.md`
2. 提交到 git
3. 要求用户审查
4. 开始按计划执行

## 使用示例

### 示例 1：用户说"实现一个登录功能"

**你应该：**
1. 🚫 不要立即开始写代码
2. ✅ 启动 Brainstorming 流程
3. ✅ 询问：这是 Web 应用还是移动应用？
4. ✅ 询问：需要支持哪些登录方式？
5. ✅ 提出 2-3 种方案
6. ✅ 呈现设计并获得批准
7. ✅ 编写设计文档
8. ✅ 创建实现计划
9. ✅ 使用 TDD 方式实现

### 示例 2：用户说"用 TDD 方式实现计算器"

**你应该：**
1. ✅ 确认已有设计（如果没有，先 Brainstorming）
2. ✅ 编写第一个测试（加法）
3. ✅ 运行测试，确认失败（RED）
4. ✅ 实现加法功能
5. ✅ 运行测试，确认通过（GREEN）
6. ✅ 重构代码（REFACTOR）
7. ✅ 重复循环（减法、乘法、除法）

### 示例 3：用户说"登录功能不工作了"

**你应该：**
1. ✅ 启动 Systematic Debugging 流程
2. ✅ 要求用户提供复现步骤
3. ✅ 尝试复现问题
4. ✅ 添加日志定位问题
5. ✅ 使用二分法缩小范围
6. ✅ 提出根因假设
7. ✅ 验证假设
8. ✅ 实施修复
9. ✅ 添加回归测试

## 关键提醒

### 何时必须使用 Superpowers

✅ **必须使用：**
- 生产级代码开发
- 需要长期维护的项目
- 团队协作项目
- 复杂功能实现

❌ **可选：**
- 快速原型验证（但验证后应该用 Superpowers 重写）
- 一次性脚本（但如果变成长期维护的代码，应该补充）

### 记住

- **Superpowers 不是建议，是强制流程**
- **每个项目都要经过 Brainstorming，无论多简单**
- **TDD 不是可选的，是必须的**
- **调试要系统化，不要随机尝试**
- **计划要详细，任务要小**
