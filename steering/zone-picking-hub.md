## 四、一期关键踩坑清单

**业务红线**
1. **约束 26 兼容性红线**：Zone Picking 只上 002 仓，001/101 行为必须与上线前一致。所有 Zone 逻辑放在 `ZonePickingSwitchGuard.isDisabled(zoneConfigService, wh)` 短路之后；测试构造 001 仓场景时断言「零 DB 访问、零写操作」。
2. **代码与 spec 冲突不自行选边**：把「Dxx 说 A，代码是 B」摆给用户裁决。用户要求改实现时走 HANDOFF §12 五步流程，最后一步必须同步 spec（tasks 加变更记录、design 追加 D31+），否则后续会话会把改动「修」回去。
3. **禁止为了让测试变绿回退实现**：一期剩余失败几乎都是断言过时，先读 tasks.md 对应任务确认新口径再改测试。

**高危耦合点（改之前把牵连位置全看一遍，详见 HANDOFF §12.3）**
4. Cart 释放唯一入口 `CartReleaseService.releaseIfEmpty`，唯一触发点是打包完成钩子；上车链路恒不释放 Cart。
5. Slot 释放 `SlotReleaseService.releaseIfNoCart` 只有两个触发点（Cart 上车、合并完成）；OOS 与 Batch 解散禁止调用；换绑后的原格口释放必须在事务提交后调用。
6. `bindZoneCartToSlot` 被 `handleCrossZonePickingFinish` 三个分支共用，主从差异只在入口内按 `is_primary` 区分；只有 Main_Zone 侧同步主表快照和推进就绪。
7. 格口校验两层 vs 三层：三层（含 Zone 归属）只用于 `pickingTaskFinish` 带 Slot 与 `bindZoneCartToSlot`；`confirmToteArrival`、`changeConsolidationSlot`、`scanSlot` 用两层，给它们加 Zone 判据会线上误拒。
8. 判定口径一律取 `wh_consolidation_task_detail`；主表 `primary_cart_no`/`consolidation_no` 只是 Main_Zone 侧冗余快照。

**数据与 SQL**
9. **历史数据不动，查询侧过滤**：`wh_picking_order.tote_no` 记录真实使用过的 tote，合并完成后 tote 被复用导致「reference to multiple orders」时，在 SQL 加 `NOT EXISTS`（`is_primary=0` 且 `ct.status=80`）排除，不要改字段（改成 Zone1 tote 会让 Cart 永不释放）。逐个 tote 合并时警惕中间状态污染下一次判断。
10. **多服务同名逻辑要一起改**：`queryPackingInfoList` 在 wms-cloud-service 与 central-packing-service 各有一份，修一处立即 grep 另一处。
11. UPDATE 明细必须带 `picking_task_id` 等任务级约束，只按 `cart_no` 更新会在 Cart 复用时误更历史任务（Bug#10279）。
12. UAT 初始化（2026-10-28 实查已更新）：一期增量 DDL 已执行，`location_type=51` 已有 40 个格口 `Z1CS001~020`、`Z2CS001~020`（格口编码正则 `^Z(\d+)CS(\d+)$`，DDL 注释里的 `CON` 前缀已过时），HANDOFF §13「半初始化」描述过时。全量脚本 Part 3 有三处坑：`wh_zone_config` 写的是 001（应为 002，漏改会导致全部库位被判无 Zone 而拒绝拆分）、`wh_location_type` 用 `INSERT INTO` 非 `INSERT IGNORE`、库名 `Yamibuy_WH` 与 `yamibuy_wh` 大小写不一致。DDL/数据初始化按发布流程走，模型不代执行。

**二期新增（OP-40026）**
29. 优先级不要只看 Sheet 的「梯度×100 + x/y×100」：那只是自动层（几百）。生产 002 仓几百万到上千万的值是 Central「↑」按 `1,000,000 + 全仓 status=1 最大值` 逐级叠出来的，每周 13%–33% 的 Batch 被 ↑。新加权不能直接加在 `batch_priority` 上（`+100000` 对 ↑ 过的 Batch 无效）。改优先级前先读 skill `wms-batch-priority-guide` 和 `docs/active/OP-40026-zone-picking-phase2/priority-analysis.md`。
30. 格口一格多车：Consolidation Slot（`location_type=51`，`Z1CS/Z2CS`）与 Parking Slot（`wh_parking_slot`，`PRK*`/`Z1PS*`）都允许多台车同时停放，车与格口关系在 `wh_picking_cart.parking_slot` + `park_type`（2=Consolidation，1=Parking）。实查 `Z2CS006` 停 10 台、`Z1CS004` 停 68 台。
31. 无 Tote 的车库存在车上：PW 车（`wh_picking_order` 无 tote_no，库存在与车同号的 `location_type=33` PW 框）与全 2-Day / HI、AK 的单 Zone Zone 2 Batch 车（Bug#10363）都不绑 Tote，一期以 Cart 号作 Tote 占位（`toteNo==cartNo`，`TruckManagementServiceImpl` 约 703–724 行）直上卡车，PW 合单以 Zone 2 PW 车为转出库位。凡是「上车释放车」「按 Tote 上托盘」「按 Tote 识别上车记录」的设计都要单独处理这类车，否则订单卡死或库存挂在空闲车上（OP-40026 审查 H1）。
32. PW 车号 = PW 框号：`OrderPickService.bindToteForCartNo` 用车号查 `location_type=33` 的框（查不到报 `this tote not exists`），所以 PRD 里 Putwall 车 `Z2PW…` 与 PW Tote `Z2PW…` 同号是设计如此，不是扫码冲突；初始化新 PW 车时必须同时建同号的 33 类库位。`wh_batch_zone.status` 只有 0 待拉取 / 1 已拉取，没有完成态。
33. 打包与补单按 `wh_picking_order.cart_no` 历史值释放车：一期约定进停车流程的订单记 cart_no、车留到打包，不进的置空（`OrderPickMapper.updateOrderCartByTask`）。central-packing-service `PackingService.processOrderInfo` 按 cart_no 清车的当前停放并减 `wh_parking_slot.cart_count`，`unbindCartAndTote` 在旧任务计数为 0 时按 cart_no 置车可用；wms-cloud-service `ReplenishService.unbindCartAndTote` 同样按 cart_no 释放，且 `queryOrderCountByCartAndOrder` 把 cart_no 传成仓库号、计数恒为 0。凡是在打包前释放车的设计（如二期上车释放 Tote 型车），必须同时清空这些订单的 `wh_picking_order.cart_no`，或在这些释放点比对车当前 picking_task_id，否则会释放新任务正在用的车（OP-40026 第 3 轮审查 R3-H1）。
34. 商品行也带任务号：`wh_picking_order_item.picking_task_id` 在拆分时写入，拣货清单、绑框、扫 Tote 与打包查询都按它过滤（`item.picking_task_id = #{picking_task_id}` 或 `a.picking_task_id = b.picking_task_id`）。把订单从一个任务改挂到另一个任务（如 Group 领取改挂、Break / Create Group）时，`wh_picking_order` 与 `wh_picking_order_item` 要一起改，只改 picking_order 会让商品在新任务里拣不到（OP-40026 第 3 轮审查 R3-M1）。
35. 关开关回到一期时，一期入口不认识二期对象：一期合单 `scanTote` 经 `WhConsolidationTaskDetailMapper.selectByToteNo`（`LIMIT 1`、不看 Tote 模式）只取一单，首单合完即释放 Zone 2 Tote；一期 Truck `load` 扫格口会装上格口上全部车，`unload` 经 `confirmToteArrival` 把整台车停入被扫格口。Group Tote、二期托盘上的 Tote / Cart 要在这些一期入口按数据拒绝（不随开关），不能只靠「关开关后先停作业再跑脚本」（OP-40026 第 4 轮审查 R4-M2）。
36. 状态幂等遇到「动作本身消除了前置状态」要另存结果：扫格口装托盘在同一事务内释放车与格口，网络重试看到的是空格口，若按「格口无车即拒绝」处理就丢了已生成的托盘号。这类动作要么按（车次, 格口）返回最近一次结果，要么让客户端带请求号（OP-40026 R4-M1）。
37. 守护代码要先于被守护的数据上线：按数据排除新对象的代码（如 Group 模式的车 / Tote 不进一期 Zone2 Print 分配、不过 `checkToteMatch`）随后端发布，被排除的数据（D1 / D2 的 GZ2M、GZ2T）就不能先于后端初始化，或先以不可分配状态插入。Zone2Print 分配 SQL `ORDER BY rec_id ASC`，新行排在后面只是降低命中概率（OP-40026 R4-M3）。
38. Dashboard 有按车号前缀的统计：wms-analytics-service `WMSDashBoardMapper.getOutboundBPCycleTime`（`cart_no LIKE 'M%' / 'L%' / 'YML%'`）与 `getOutboundPWCycleTime`（`'PW%' / 'PL%'`），新编码 `Z2M` / `GZ2M` / `Z2PW` 拣的订单会从这些指标里消失；换车号编码前先 grep 各服务的 `LIKE '前缀%'` 与 `startsWith`（OP-40026 R4-L8）。

156. 并发写法的三条规律（OP-40026 5.4–5.6）：① 「先 CAS 父行、再收子行」（Finish Loading 先把车次 Loading → In Transit，再收本车次托盘行），收子行用当前读（`FOR UPDATE` 或直接按父键 UPDATE），不要靠普通 SELECT；另一方（扫格口写托盘行）写子行前对父行 `FOR UPDATE` 并确认状态，两边以父行为唯一交叉点。② 「子行全部完成才推进父行」（最后一个托盘下车才把车次置 Unloaded），事务第一步 `FOR UPDATE` 父行让事务排队，父行的 UPDATE 把条件写进语句 `AND NOT EXISTS (SELECT 1 FROM 子表 WHERE … 未完成)`（UPDATE 里的子查询是当前读）；只靠「父行锁 + 普通读」也对，但以后有人在前面加一条普通读，快照就提前了，单测发现不了。③ 两条 UPDATE 各写 `UNIX_TIMESTAMP()` 跨秒会差 1 秒，要求两处时间一致时先写一处、同一事务读回，再作为参数传给另一条；同一条语句里多次 `UNIX_TIMESTAMP()` 取值相同。

Spock 2.3 交互匹配规则（本项目踩过的）：① 响应闭包只有一个参数、且类型能接住 List（不写类型、`Object`、`List<X>`）时，拿到的是整个参数列表，单个 List 实参写 `{ args -> args[0] }`，多个参数时才逐个展开；② 同一调用匹配多条交互时先声明的胜出，then 块的交互优先于 setup / given 的桩，所以 setup 给默认值、given 再写 `>>` 不生效，要改值就让 setup 的桩读字段（`>> { flag }`）或把交互写进 then；③ 有序 then 块里的 `0 * mock._` 会先拦截 when 期间该 mock 的全部调用；④ 把零写入断言抽成辅助方法时，then 块里要写 `interaction { assertNoWrite() }`，直接调用会空转；⑤ 普通辅助方法里写 `mock.m(_) >> {…}` 不生效（`>>` 被当成右移），共用桩放抽象基类的 `setup()`；⑥ where 块只能读 `@Shared` 与 static 字段，按行选 mock 时放字段名字符串、方法里用 `this."${name}"` 取；⑦ `Stub` 对 Integer 返回 0（`Mock` 才返回 null），被测代码按 `!= null` 判「查到了」时要显式 `>> null`；⑧ 交互的方法名可以写 GString（`1 * mock."${methodName}"(*_)` 精确匹配）；⑨ 既要桩返回又要计数时，setup 里写 `>> { calls.x++; db.x ?: [] }`（`calls = [:].withDefault { 0 }`），then 只断言 `calls.x == 1`；⑩ 用例名里数据变量后面直接跟点号（`#alias.first_claim_dtm`）会被当成取属性，报 Unroll 表达式错误（OP-40026 各线）。
